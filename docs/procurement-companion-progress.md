# Procurement companion: search candidate boundary

Status: candidate-boundary fix deployed and all 11 query grids verified in an authenticated production desktop browser. See `live-search-audit-2026-10-08.md` for exact rendered IDs and limitations. This is not completion of the procurement companion programme.

## Findings and changes

- The previous UI used the complete visible catalogue when an action had no terms, then prepended backend ranked IDs. A backend response with IDs and empty terms could therefore retain unrelated products.
- Candidate composition now has an explicit search/browse boundary. Search without terms or grounded IDs returns no candidates. Ordinary model searches render only its valid, customer-visible IDs. Verified medical searches preserve the complete verified local membership set; model IDs can reorder that set but cannot introduce unrelated products.
- Local Product Knowledge Index retrieval remains constrained when the backend fails. Clearing search restores browsing.
- Search counts say “matching products”; browse counts say “products”. The landing depth statistic remains separate.
- Category hero totals now update with the rendered grid while typing. The mobile request summary remains hidden while search controls retain focus, preventing it from intercepting Clear.
- Blood-pressure cuffs no longer inherit monitor aliases. Cuff queries retain their own accessory concept. Large gauze search uses the indexed large-size attributes rather than merely demoting small products. Explicit non-sterile descriptions no longer gain the sterile alias.

## Counts and provenance

The build index contains 685 controlled records, including 613 marked customer-visible in the frozen catalogue. Hidden records may be indexed for maintenance but are excluded by the customer candidate boundary. The authenticated storefront can replace visibility and merge newly published institutional products from `published_storefront_catalogue`; therefore its current visible catalogue-line total can differ from the frozen build count. The previously observed 664-line customer screenshot is a runtime storefront count, not a search result or a claim that 664 indexed records matched a query. Its exact current value still requires authenticated browser verification.

The rendered search result count is calculated from the same filtered candidate array used to create the product cards. Verified ingredient/class metadata remains separate from commercial records. No medicinal facts were generated by this change.
